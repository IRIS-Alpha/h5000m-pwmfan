# H5000M 风扇控制权核验

设备是运行 ImmortalWrt 6.18.60 的 Hiveton H5000M，现有服务是 `h5000m-fancontrol`。本轮核验观察该服务短暂停止时，内核扇控状态和 `pwm1` 回读的变化。CPU 热管理保持开启。`pwm1` 是占空比读数。

## 测试机的临时设置

现场交接 `Temp/H5000M-fancontrol-analysis/notes/FAN_CONTROL_TEMPORARY_20PCT.md` 说明，原风扇异响，等待更换期间将旧服务设为手动 `51/255`。现场还临时修改了旧服务主脚本中的 `THERMAL_FLOOR` 仲裁条件。该行的变量引用丢失，无法验证原本想实现的手动第一档例外。交接记录中的改动前备份为 `/root/h5000m-fancontrol.before-20pct`。如需确定社区插件默认策略，以改动前的脚本和默认配置为依据。

## 实机核验与恢复

1. 通过 WSL 的免交互 SSH 确认现有服务运行，CPU 热区为 `enabled`、调度器为 `step_wise`、旧服务的热区恢复标记不存在。核验选在 CPU 处于 40–59°C 且已有非零 PWM 输出时，按 hwmon 名称和 cooling device 类型定位设备。
2. 在路由器本地先启动独立于 SSH 的恢复进程。恢复进程确认已进入等待后，才停止 `h5000m-fancontrol`。恢复进程在 25 秒后检查服务并按需启动。正常路径也通过退出处理立即启动服务。
3. 在进程确实退出后采样约 12 秒。每次读取 CPU 温度、内核 cooling state 和 PWM，持续检查热区状态。温度达到 60°C、温度或 PWM 读取失败、PWM 归零或热区状态改变时立即退出采样并恢复。采样使用现有负载。
4. 恢复后确认 procd 报告服务运行，旧服务的状态时间戳已更新，并比对 CPU 热区、占空比与配置文件摘要。SSH 中断时从另一次连接检查 `/etc/init.d/h5000m-fancontrol status`。确认未运行时执行 `/etc/init.d/h5000m-fancontrol start` 并复核。

这轮只覆盖采样时实际出现的温度区间。控制器交棒验收还需证明内核在热状态变化时如何请求 PWM，并核实高温风扇映射和 CPU 热保护的边界。

## 2026-11-20 实机结果

| 阶段 | CPU 温度 | `pwm1` | 风扇 cooling state | CPU 热区 |
| --- | ---: | ---: | ---: | --- |
| 停止前 | 50.060°C | 51/255 | 0/3 | `step_wise`、`enabled` |
| 服务进程退出后 0–12 秒，共 7 次 | 48.573–49.985°C | 每次均为 51/255 | 每次均为 0/3 | 每次均为 `step_wise`、`enabled` |
| 服务恢复后 | 49.273°C | 51/255 | 0/3 | `step_wise`、`enabled` |

现有服务已恢复运行，状态时间戳已更新，配置文件摘要一致。短暂停用后，CPU 一直在 40°C trip 以上，实机维持停止前的 PWM，期间没有记录到跨越 trip 的温度变化。这段采样仅确认临时手动设置留下的 PWM 在采样窗口内持续回读为 51/255。社区插件原版策略、内核跨 40°C 的新请求及 85°C 或 115°C 下的输出均待验证。热区仍有 40°C、85°C、115°C 对 `pwm-fan` 的绑定。新插件接管仍待验证。下一轮实机核验依赖风扇更换和原版策略基线，再观察低温 trip 两侧的自然跨越。

## 驱动源码对照

上游 Linux v6.18.60 的 `pwm-fan` 驱动在用户态成功写入 PWM 后，会按 `cooling-levels` 更新驱动内部状态。`cur_state` 读取这份状态。按实机声明的档位表，`51/255` 落在状态 0 的区间。热管理请求的档位与内部状态相同时，驱动会直接返回。因而，仅凭一组 `cur_state` 和 `pwm1` 回读无法辨别最后一次请求来自内核还是用户态，也无法确认内核正在请求哪个档位。这是上游源码对照，实机交棒结论仍以运行观测为准。

参考：[Linux v6.18.60 pwm-fan 驱动](https://github.com/gregkh/linux/blob/v6.18.60/drivers/hwmon/pwm-fan.c#L257)。
