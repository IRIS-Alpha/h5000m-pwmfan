## 保护功能调查与待定定义

本功能暂名为“温度保护”。检查了固件中的旧 `luci-app-h5000m-fancontrol` 控制器，以及本包 `h5000m-pwmfan` 控制器；两者的自动/曲线调速均没有“温度异常时在曲线请求上加 20 个百分点”的实现。

- 旧 `h5000m-fancontrol`：自动模式先由选定温度源计算曲线 PWM，再将 CPU thermal cooling map 得出的 cooling floor、5G modem throttle floor 与曲线请求取较高值。若无法取得有效控制温度或曲线无效，使用故障全速输出。CPU trip/map 优先从设备树读取；旧固件回退阈值为 38°C、83°C、113°C，对应 cooling state，再映射到 PWM cooling level。进入 `kernel` 模式会释放用户态热控并由内核路径负责。
- 新 `h5000m-pwmfan`：收集可用温度源，最高有效温度用于独立的高温判断；默认 `safety_temp=85°C`，达到阈值即直接请求 PWM 255（100%），否则按模式曲线计算。5G modem thermal throttle 可设置请求下限。没有有效温度、配置/曲线无效或 PWM 写入失败时走全速故障策略；`kernel` 模式释放插件控制权。
- 这两类逻辑需区分：高温阈值触发属于有效读数下的温度保护；传感器缺失/故障、配置异常、写入失败属于故障全速；CPU thermal cooling floor 和 modem throttle floor 则是其他控制来源提出的输出下限。它们都不是曲线输出 +20 个百分点。
- `kernel`/未接管是控制权归属，不等于插件温度保护正在运行。内核自主时插件不应再叠加自己的 PWM 增量；如果以后支持保护增强，须先明确 ownership、内核 cooling map 和插件写入之间的仲裁。

## 11. 讨论补充（问题 1、5、6）

### 11.1 内核独立风扇请求与保护状态

静态固件证据包括 Linux `pwm-fan.ko`；原风扇服务读取 `/sys/class/thermal/cooling_device*`、设备树 `cooling-levels`、thermal trips 和 cooling maps；旧插件的 `kernel` 模式会释放其用户态控制。这说明固件具备内核 cooling-device 接口，也说明旧插件设计了回退路径，但不能证明插件服务停止时某个 cooling map 实际生效，更不能单独确定每个 trip 对应的 PWM 数值。

实现前需对照同一设备的运行时证据：

1. 只读记录 thermal zone 的类型、温度和 policy，各 cooling device 的类型、`cur_state`、`max_state`，以及 live device tree 中 `pwm-fan/cooling-levels` 和 thermal-zone trips/cooling-maps。
2. 同时记录 hwmon PWM 回读和可用转速反馈；将 cooling state 映射到设备树 cooling-levels，确认单位与数值。`cur_state` 可能被直接 PWM 写入同步改变，不能仅凭单次状态断言请求方是谁。
3. 先在不改动服务或 PWM 的情况下采集当前状态和日志；若还需验证停止插件后的行为，应另做有温度监控、可立即恢复、有人在场的受控实验，并预先确认安全边界。不能直接在线停止现有散热服务来试验。
4. 覆盖低温、trip 附近及高温保护状态；确认 policy、请求状态、PWM 实际值与 RPM 是否对应。无法安全制造的温度只能从设备树和驱动契约推导，并标记未实测。

状态建议拆成三类：

- **未接管 / 内核自主**：证据表明内核 cooling device、trip、policy 和 PWM 映射能独立提供可接受调速与过温响应；插件不主动持有 PWM，只读显示。
- **已接管 / 插件控制**：内核没有有效 cooling map、请求始终为固定满速或无法完成预期调速；插件按曲线控制 PWM，同时保留 CPU thermal trips 和故障全速保护。此时不能说是内核在控制风扇。
- **状态未知 / 冲突**：不能确认 ownership 或 cooling state 与实际 PWM 的关系时，不自动切换所有权，也不显示已接管/未接管结论；显示警示并维持预先定义的保守运行策略。

“内核能控速”与“内核只在过热时兜底”需要分开判定。内核若只在高温通过 trip 提升 cooling state，低温区不请求输出，可能是正常按需冷却策略，不应仅因低温 PWM 为 0 就判断它不会保护；若始终请求 100%，则是有请求但策略可能不可接受，是否由插件接管须以固件设计/用户选择为准。状态灯代表控制权归属，不承诺风扇必然转动；实际 PWM 和 RPM（若有）单独显示。

板卡图片只说明 PCB 元件/接口位置，未提供 PWM 接线、风扇额定值、设备树 trip 或 cooling-levels，不可据此推导内核请求参数。

### 11.2 双图采用同一视觉语言

吞吐量图是滚动时间序列组件，不能把其采样/历史语义套到静态风扇策略曲线。可共享主题色、网格与轴线、线宽、曲线端点、图例位置、游标和浮层排版。静态图保留温度 X 轴、输出 Y 轴、真实控制节点和首尾水平延长；历史图保留时间 X 轴与四个温度序列。

两图都可显示纵向游标及其穿过位置的 Y 轴读数，但读数来源不同：静态图显示游标温度对应的插值输出；历史图显示该时刻各有效温度。当前传感器、请求、回读和保护状态继续由看板展现，避免将动态看板值伪装成静态曲线上同一时刻的观测值。

曲线手势分为只读游标和拖拽编辑：非手动模式永远只读、不捕获拖拽；手动模式下只有按中明确节点才拖动，图面其他位置用于游标或页面滚动。移动端如触摸游标与纵向滚动冲突，优先保障页面滚动，可点击定位游标，节点单独拖动。

### 11.3 固定节点与温度停转区

固定节点数量可简化增删、移动端布局和前后端校验，建议首版固定六个真实节点，不提供添加/删除点。每点温度可编辑，但须严格递增且在全局范围内；输出必须非递减。每点显示有效范围，提交时校验整条曲线。预设只读，选择手动后才可编辑。

固定节点可能使简单曲线产生冗余点，也增加用户需要理解的参数数量；允许相邻点输出相等形成平台，但温度坐标仍严格递增以避免插值除零。若实测只需四个拐点，后续可改固定四点；不建议首版同时实现可变点数和复杂区间约束。

节点之间按**分段线性插值**计算：对温度 `T` 落在 `(T1, PWM1)` 与 `(T2, PWM2)` 之间的情况，目标 PWM 为 `PWM1 + (T-T1) × (PWM2-PWM1) ÷ (T2-T1)`，最终量化到驱动接受的整数 PWM。各段可以有不同斜率；六个节点不会让整条曲线成为一条全局直线。低于第一点温度时保持第一点输出，高于最后一点温度时保持最后一点输出。当前后端 `curve_value()` 已采用这种线性插值和端点保持，shell 整数运算会截去小数部分；后续 UI 绘图应匹配量化后的控制结果或清楚说明绘制为连续近似。

“最低运行输出”不能简单作为曲线全局下限。低温时用户可明确配置 0%（停转区）；曲线请求大于 0% 后，才应用经硬件验证的最低稳定运行 PWM；高温、内核 cooling request、故障保护可进一步提高输出。需要区分“0% 停转区”和“风扇已启动后的最低稳定输出”。固定六点能描述停转区边界，但这是允许停转，不代表保护失效。在测得最低起转值前，不应让 20% 同时承担冷却下限和电机稳定起转保证。

- 问题 1：先建立只读 ownership/thermal 证据表，再确定未接管/已接管语义与默认行为；不要先做含糊的保护开关。

- 问题 6：用户接受固定节点方向，建议首版固定六点，允许编辑温度并校验温度递增、输出非递减；相邻点之间为分段线性插值。另行定义 0% 停转区和已启动最低稳定输出。
- 问题 1：用户确认按此前的内核自主/插件接管/状态未知方案继续；接管判断仍需只读 thermal/cooling 证据，服务停止后的请求值未验证。

### 调度与目标驱动

- 快速调度为安静、平衡、性能、目标驱动、手动五种模式；停转由固定请求的 0% 表达，`mode=off` 已退场，允许列表不再接受该值；保护覆盖仍可提升输出。

- 目标驱动使用线性前馈曲线加有界 PI 修正，无 RPM 闭环，不开放节点编辑。用户参数：目标温度 `T_target` 80–100°C；界面名称使用“响应区间” `R_response`，最低 15°C，最高受温度区间限制，要求 `T_target - R_response >= 0°C`；低温过渡宽度 `H_blend` 为 2–10°C，默认 5°C。若 `H_blend > T_target - R_response`，计算时自动压缩为 `T_target - R_response`，使过渡起点不低于 0°C；在该区间将低温请求线性衔接至响应曲线。
- 目标驱动低温请求沿用当前模式最低输出请求，允许 0%；从 0% 到非零时启动助推一次。PI 参数为内部实现项。保护覆盖时冻结积分，退出时避免积分突变；传感器/计算故障执行故障全速并报告原因。

### 全局温度保护

- 保护始终参与，是最高优先级覆盖层，不是快速模式。阈值默认 90°C、可调 80–100°C；加速半径至少 15°C，允许目标温度等于保护阈值。
- 进入加速半径时助推一次，随后随温度渐进提高请求；到阈值锁定 100%，绕过斜率限制和死区。
- 降至 `T_global - H_release` 或更低才解锁。`H_release` 独立设置，最低 2°C，不与 `H_blend` 共用字段或校验。
- 每个锁定周期计数一次；显示近 24 小时/累计次数、最近触发时间和周期峰值，不用未经实测的次数阈值判定错误。
- 仲裁意图：故障全速 > 全局保护锁定 > 内核 100°C 以上请求 > 目标驱动/曲线 > 手动/停转（固定请求 0%）。内核与插件真实仲裁须运行时验证；来源不明显示未知。若 40°C/85°C cooling map 覆盖插件请求，先完成实测和回滚评估再决定集成改动。

1. 先只读采集 thermal zone、trip、governor、cooling device、pwm-fan 请求/状态和插件运行/停止时 PWM 回读，记录来源及观测限制。

## 16. 应用模型与提交合并

日期：2026-11-22。已确认“分控件”策略；后端不做固定请求步进限幅。

- 模式与曲线预设切换：选中态立即更新，实际提交在最后一次点击后 3 秒触发（只执行最后一次）；等待期间在“固定请求/曲线预设”标题行的状态位显示“应用中-Ns”，N 为剩余秒数（3→1），提交被状态回读确认后回到已选/未选。
- 固定请求滑块与加减按钮：拖动过程只更新读数与浮动气泡，松手才提交；提交同样进入 3 秒尾随合并窗口，与模式切换共用同一个合并器，手速档的中间值不写入配置。0% 例外：拖到 0% 或按减号到 0% 时绕过合并窗口立即提交，停转不等待冷却。
- 高级设置表单：保持 LuCI 的“保存并应用”，不进入合并窗口。
- 定温驱动参数与自定义曲线点：不进入合并窗口，也不随输入即时生效；编辑后“曲线预设”标题行的状态位显示“待应用”，点“应用目标”/“应用曲线”才提交，提交被状态回读确认后回到已选。定温驱动参数另提供“撤销”按钮恢复已保存值。
- 历史图窗口与采样间隔：本地即时生效，持久化写入可延迟合并。
- 后端不做固定请求步进限幅：0% 必须立即生效，手速档的中间值由合并窗口消化。
- 哪些模式吃降速兜底：只有温度驱动的请求（`mode=target`、`mode=custom`，或安静/平衡/性能的 `drive=curve`）保留回差保持与降速等待；占空比类请求（固定请求，以及 `drive=duty` 的安静/平衡/性能）一旦数值下降就立刻下发，人为改的占空比不该被温度回差拖住（`hold_down_allowed()`）。
- 同值提交不落盘：界面提交前先比对当前配置，没有实际差异就跳过 `uci.save()`/`uci.apply()`，快速“加一格再减一格”不再触发一次带重载的下发。
- 下发瞬时失败重试一次：`uci.apply` 偶发返回 ubus code 5（无已接收数据）时自动重试一次，仍失败才回滚并提示，避免连续点击时弹出误报。
- 提交期间控件不禁用：加减、滑块、模式按钮保持可点，落在下发期间的改动进入同一个队列，等当前下发结束后再按合并窗口执行，因此连续点击不会丢操作。
- 提交在 `pagehide`/`visibilitychange` 时冲刷，避免关页丢失。
- 判断“是否真的生效”：重试后仍返回 code 5 时先读 `uci changes`；该配置已无暂存项即视为已生效，不弹红色提示（“无已接收数据”也可能意味着后端没有可应用的内容）。
- 下发失败时丢弃暂存：确认失败后调用 `uci revert` 并重新加载该配置，页面回到已保存值；不再用“恢复旧值再 save”的方式收尾，因此不会残留“未保存的更改”标记，也不会把失败值留在待提交状态。

## 17. 内核风扇交棒（全局接管）

日期：2026-11-22。决策：启用接管时，插件在全部温度区间驱动风扇，不再把内核热区当作风扇保护层。

- 语义：启用接管且通过核验后，插件在所有温度区间驱动 `pwm1`；不再出现“高于 100 °C 由内核热区接管风扇”的说法。CPU 降频（passive trip）与 125 °C 临界关机仍由内核负责，不受插件影响。
- 依据：`pwm_fan_write()` 每次写入都会把驱动缓存状态重置为 0（`pwm_fan_update_state(ctx, val)`），`pwm_fan_set_cur_state()` 只在目标状态与缓存不同才下发档位，因此用户态每个控制周期写入都会让 governor 在 40/85/115 °C 设置的档位只生效不到一个周期。设备实测：`cooling-levels = 0,128,192,255`，`cdev2/cdev1/cdev0` 分别绑定 40/85/115 °C。
- 门槛：`kernel_takeover=1` 单独不足以接管，必须同时 `takeover_verified=1`（`root/etc/config/h5000m_pwmfan` 默认 0），且被控 PWM 可写、`/sys/class/thermal` 下存在 `type` 为 `pwm-fan` 的冷却设备；否则守护进程继续报 `state=disabled reason=takeover_pending` 并释放风扇。
- 核验：`takeover_verified` 只能在一轮有界实测之后由人工置 1；实测步骤与回滚命令见 `docs/KERNEL_HANDOVER.md`。
- 文案：高级设置中该项标签为“接管风扇控制”，说明为“启用后，插件在全部温度区间驱动风扇；CPU 降频与临界关机仍由内核负责。完成交棒核验后才会实际接管。”
- 安全余量：插件温度保护阈值默认 90 °C（可调 80–100），高于内核 85 °C 的 192/255 档位，全局接管不削弱过温响应。
- 实测（2026-11-22，已批准）：`takeover_verified=1` 后插件接管，`pwm1` 跟随请求（安静 70% → 179/255），内核 `cur_state` 保持 1 但被写入覆盖；停下插件时写入 `FAILSAFE_PWM`（255，全速释放），重启旧守护后回到 51/255。旧服务已停用并取消开机自启，`/etc/rc.d` 只保留 `S95h5000m-pwmfan`。

### 17.1 触点上调（2026-11-22 批准）

内核 `step_wise` 只在下发档位变化时写 PWM，而插件每 2 s 的读回校验会发现 `pwm1` 被改成 0 并立刻写回，于是 40 °C 触点附近会出现“内核写 0 → 插件写回”的往复，用户能在 1–2 s 内听到风扇停转。实测日志（2026-11-22 17:21、17:22）中 `pwm 0 -> 191` 两次修正与两次停顿时刻完全吻合。

- 接管启动时由插件上调两个最冷的 `pwm-fan` 触点：`trip_point_5_temp` 40000 → 1000（内核不再请求 0%），`trip_point_4_temp` 85000 → 114000（= 下一个触点 115000 − 1000，内核不再用 192/255 覆盖可配置过温策略）。
- 115 °C（255）与 125 °C（critical）保持不动：插件过温保护在上限时正是 255，两者不冲突，内核的临界关机仍是独立兜底。
- 只在接管生效期间修改，并把原值记录到 `$RUNDIR/thermal-takeover`；释放风扇、`mode=kernel` 或退出时恢复 40000/85000，写入失败会记日志。
- 启动时检查热区 `policy`，若为 `user_space` 则恢复为 `step_wise`（历史版本可能留下该状态），插件从不把整区改成 `user_space`。
- 过温保护阈值可继续在 80–100 °C 调整；此时内核已无风扇触点，插件曲线是唯一的风扇保护层，`thermal_floor` 只写入状态文件，不参与决策。
